# Review, feat/subscription-checkout-stripe-webhook, 2026-09-11

**Reviewed by**: Claude Sonnet 5 (author on an earlier model)
**Scope**: 35 files, branch vs base (main, merge base e571ff8)
**Verdict**: Changes requested

## Summary
This is a careful, well documented implementation of spec 0007: hosted Checkout, the Billing Portal, and a hand rolled webhook that verifies, resolves the org, re reads authoritative state outside the transaction, and applies it behind a row lock with a conflict do nothing ledger. The six step ordering the spec calls out as "the part most easily got subtly wrong" is followed correctly, including AC-24 (the Stripe round trip really does happen before `db.transaction` opens, confirmed by reading `src/payments/webhook.ts`). The database-backed test suite is genuinely thorough: replay, reordering, rollback, concurrency and poison events are all proven against real PostgreSQL rather than a mock. That said, three things need attention before merge: part of the webhook's own logging promise (AC-21) is silently skipped on some failure paths, the new error boundary uses a prop that no longer does a full retry under Next 16, and the two Server Actions that actually create Stripe sessions have no automated test at all.

## Major

### 🟠 AC-21's logging promise is not kept on every 500 path, `src/payments/webhook.ts:336-369`
**Problem**: The structured log line only fires through the `answer()` helper, which is called on the paths inside the two `try` blocks (verify, and the transaction). Three ways this handler can reach a 500 skip it entirely: a re-thrown Zod parse failure at line 350 (`throw thrown;`, deliberately not caught), `resolveOrgId`'s own `db.select()` at line 353, and `organizationExists`'s `db.select()` at line 364. None of these three sit inside a `try`, so if any of them throws, the exception propagates straight out of `handleStripeWebhook`, out of the route handler, and Next's own default handling turns it into a 500 with no call to `logStripeWebhook` at all.
**Why it matters**: AC-21 is explicit and unconditional: "A webhook failure logs the event id, event type and error in one structured line before the 500 is returned." The gap is worst exactly where it matters most: a Zod parse failure on this path means Stripe's shapes moved under the code (the exact "loud on purpose" scenario the comment names), and that is precisely the failure an operator most needs a log line to diagnose quickly. There is no Sentry or `instrumentation.ts` fallback yet in this repo (feature 20 is still ahead), so today these three paths are completely silent 500s. `verify.md`'s own AC-21 step is unchecked, so nothing, manual or automated, has caught this yet.
**Suggested fix**: Wrap the whole body of `handleStripeWebhook` from the parse of `retrievedSubscription` onward in one `try`/`catch` (or add a second one around `resolveOrgId` and `organizationExists`), and route every path that isn't already inside the transaction's own `try` through the same `answer()` call so a log line is guaranteed before any 500 leaves this function.

### 🟠 The new error boundary uses the pre-Next-16 `reset` prop, which does not actually retry, `src/app/(agency)/billing/error.tsx:19-24`
**Problem**: `BillingError` destructures `reset` and wires it to the "Try again" button. Next 16's `error.js` boundary (confirmed against `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/error.md` and the installed runtime at `node_modules/next/dist/client/components/error-boundary.js`) still passes a `reset` prop for backward compatibility, but it now also passes `retry`, and the two are not equivalent: `reset` only clears the boundary's local state (`setState({ error: null })`), while `retry` calls `context.refresh()` inside a transition *before* resetting, which is what actually asks Next to re-fetch and re-render the failed segment. Calling `reset()` alone re-renders the same already-failed children with no new data fetch, so for a Server Component read failure like this one, clicking "Try again" will typically just flash and immediately show the same error again rather than retrying the read.
**Why it matters**: The whole point of this boundary's one button is to let an admin recover from a transient read failure without a manual reload. As written, it does not reliably do that, which is the exact class of bug AGENTS.md and the vendored `nextjs-v16` skill exist to catch ("This version has breaking changes... read the docs before writing any code. Heed deprecation notices."). Worth knowing: this is not new to this PR, `src/app/error.tsx` and `src/app/global-error.tsx` already use the same stale prop, so this file is following an existing (also broken) project convention rather than introducing it. That makes it worth a repo-wide fix rather than a one-line patch here alone, but the file under review should not extend the same bug.
**Suggested fix**: Destructure `retry` instead of `reset` (or accept both and prefer `retry`) and wire it to the button's `onClick`. Consider raising a follow-up for `src/app/error.tsx` and `src/app/global-error.tsx`, which have the same issue outside this diff's scope.

### 🟠 `startCheckout` and `openBillingPortal` have no automated test coverage, `src/payments/start-checkout.ts`, `src/payments/open-billing-portal.ts`
**Problem**: Every piece of pure logic around the webhook is well tested (`idempotency.test.ts`, `billing-state.test.ts`, `events.test.ts`, the real-Postgres `webhook.db.test.ts`), but the two Server Actions that actually talk to Stripe are not exercised by any automated test. `checkoutIdempotencyKey` is tested in isolation, but the handler that decides *when* to attach an existing customer, builds the idempotency key from live state, and enforces the admin-only guard is untested. `e2e/billing.spec.ts` only covers the signed-out, no-subscription state; every authenticated path (admin vs. member, the actual Checkout Session call, the Portal call) is a manual step in `verify.md` that this session's notes say was not exercised at runtime.
**Why it matters**: This is money and permission logic in the same breath AGENTS.md's own testing gate names ("Vitest unit tests on money, permission and tenancy logic... Playwright for sign up, invite and checkout"). A regression here (say, the `existing === undefined` branch flipping, or the idempotency key silently dropping the customer id) would create duplicate Stripe customers or let a member start Checkout, and nothing in this suite would catch it before a human did.
**Suggested fix**: A unit test for each action's handler against a fake `stripeClient()` (mirroring the `StripeGateway` fake pattern already used for the webhook) would cover the customer-reuse branch, the idempotency key wiring, and the `forbidden` result for a non-admin, without needing a live Stripe account.

## Minor

### 🟡 The first-ever write for an organization is not covered by the row lock, `src/payments/webhook.ts:402-419`
**Problem**: `SELECT ... FOR UPDATE` only locks a row that already exists. When an organization has never subscribed, the select returns nothing, `existing` is `undefined`, and the `customer_id_conflict` guard is skipped entirely (there is nothing to compare against). Two genuinely concurrent *first* deliveries for the same org whose retrieved subscriptions name different Stripe customers (for example, two independent Checkout Sessions completed close together, far enough apart that the 5 minute idempotency bucket didn't dedupe them) would both pass the guard, and `onConflictDoUpdate` on `org_id` means whichever commits second silently overwrites the other's customer id.
**Why it matters**: This is the exact invariant AC-27 protects ("a stored `stripe_customer_id` is never silently replaced by a different one"), just in the narrow window before any row exists. The idempotency key makes the ordinary double-click case safe, so this is a low-probability edge rather than a routine failure, but it is a real gap in an otherwise carefully closed set of holes.
**Suggested fix**: Worth a comment at minimum noting the gap is accepted; if it's worth closing, an advisory lock keyed on `org_id` (rather than a row lock) would cover the pre-insert case too.

### 🟡 `TransactionExecutor` is re-derived instead of imported, `src/payments/webhook.ts:226-227`
**Problem**: `applyState`'s `tx` parameter is typed as `Parameters<Parameters<Database["transaction"]>[0]>[0]`, which is exactly what `src/db/tenant/executor.ts` already exports as `TransactionExecutor` (re-exported from `@/db/tenant`, which this file already imports `Database` from).
**Why it matters**: Small duplication, easy to import instead, and keeps the two definitions from drifting if the transaction signature ever changes.
**Suggested fix**: `import type { TransactionExecutor } from "@/db/tenant";` and use it directly.

## Strengths
- The six step webhook ordering (verify, resolve, retrieve outside the transaction, conflict-do-nothing ledger, lock and apply, commit) is implemented exactly as spec 0007 describes it, and AC-24 specifically checks out: `retrieveSubscription` is awaited well before `db.transaction` opens.
- `src/payments/webhook.db.test.ts` is a genuinely strong suite: it proves replay, out-of-order delivery, rollback-on-failure, true concurrent deliveries via `Promise.all` against two live connections, and the `past_due_since` database-clock rule, all against real PostgreSQL rather than a mock that would agree with a broken assumption.
- The `customer_id_conflict` guard is applied to every event type that finds an existing row, not only `checkout.session.completed` as AC-27's literal wording asks for, which is a stronger and more conservative reading of "never silently replace a stored customer id" than the letter of the acceptance criterion requires.
- `src/payments/events.ts`'s Zod schemas turn Stripe's Basil field moves (`current_period_end`, `price.id` onto the item, the invoice's subscription reference) into loud parse failures instead of silent nulls, with tests that pin the old, wrong path as a documented regression trap.
- The tenant isolation fence is respected and proven: `fence.test.ts` and `tools/eslint/tenant-isolation-config.test.mts` both confirm `withSystemAccess` is imported only by the Stripe route (plus the tenant layer's own test), matching AC-20 and spec 0003's exemption list.

## Test coverage
Strong where it counts most: the webhook's ordering, idempotency, rollback and concurrency are proven against real PostgreSQL, and the pure logic (`billing-state`, `events`, `idempotency`) is well covered with edge cases called out by name. The gap is the two Server Actions that call Stripe directly, `startCheckout` and `openBillingPortal`, which have zero automated coverage of their own branching (customer reuse, the admin guard, the idempotency key wiring) beyond the one pure helper function; see the Major finding above. AC-21's logging promise is also unproven in both directions, no automated test spies on `logStripeWebhook`, and the manual verify.md step for it is unchecked, which is how the gap in the Major finding above went unnoticed.
