# 0020. Dashboard summary

**Date**: 2026-09-24
**Status**: In Progress

## Summary

This spec replaces the placeholder on `/dashboard` with a real summary of the agency's week: a top row of four glanceable stat cards (overdue total, open projects, active clients, new deliverables), a chart of invoiced amount by month for the last six months, and the three detail sections below (overdue invoices with the total owed in each currency, open projects, and recently added deliverables), each with a headline count and its top five rows linking to the real record. Everything is read live from the tables features 11, 12 and 13 already built, through the tenant scoping layer (the code that makes every query see only the acting agency's rows). There is still no new table and no migration; the cards and the chart are new reads over the same data. Every section loads on its own (streamed, so a slow or failing one never blanks the rest of the page), and a brand new agency with no clients sees one "add your first client" state instead of five empty boxes.

## Requirements

**User stories**:
- As an agency staff member, I want to see which invoices are overdue and how much is owed, so I know who to chase today.
- As an agency staff member, I want to see our open projects, soonest due first, so I know what needs work without opening the projects list.
- As an agency staff member, I want to see the files most recently added across all projects, and whether each one is shared with the client, so I can catch a file that was meant to be shared but wasn't.
- As a new agency owner, I want the dashboard to tell me what to do first when there is nothing to summarise yet.
- As an agency staff member, I want a glanceable row of numbers at the top of the dashboard, so I know the shape of the week before I read a single list.
- As an agency owner, I want to see how much we have invoiced month by month, so I can see whether billing is trending up or down without opening every invoice.

## Decision

**Chosen option**: Option 2: Purpose built summary reads in a new `src/dashboard/` feature folder, a count plus the top 5 per section, each section streamed in its own Suspense boundary and failing on its own.

The dashboard gets its own small reads through `tenantDb`, which reuse the existing overdue, past due, date and money rules rather than copying them. The page is split into independent async Server Components, one per streamed section.

**Addendum (this update)**: the page gains two more independent sections ahead of the three original ones: an "Overview" row of four stat cards (reusing the overdue, open projects and deliverables reads, plus one new active clients count), and an "Invoiced by month" line chart (a new six month read over `invoices`). Both follow the same streamed, independently failing pattern as the original three sections. Overview's three shared cards reuse, not repeat, the detail sections' own reads: `page.tsx` starts each read once, unawaited, and passes the same promise to both consumers (see Feature design), so the addendum adds only one genuinely new read (`activeClientsCount`) plus the chart's own read. The chart is rendered with shadcn's `chart` primitive (wraps Recharts, a charting library), already the natural fit since shadcn is this project's component source and no charting library is installed yet; the runner up, a hand rolled inline SVG line, was rejected because a real multi currency, six month trend needs axes, a legend and hover detail that are not worth rebuilding by hand.

## Feature design

**Data model sketch**:

No schema change, no migration, no new index. The feature reads four existing tables, all tenant scoped by `org_id`:

| Table | Relations used | Filter | Existing index that serves it |
|---|---|---|---|
| `invoices` | N:1 `clients` (name) | `status = 'overdue'` OR (`status = 'sent'` AND `due_date < today`) | `invoices_org_id_status_due_date_idx` |
| `invoices` (addendum: chart) | none | `status IN ('sent', 'overdue', 'paid')` AND `issue_date >= window start` | `invoices_org_id_status_due_date_idx` narrows by `org_id, status`; `issue_date` is filtered in the row set it returns, same trade the overdue read already makes |
| `projects` | N:1 `clients` (name) | `archived_at IS NULL` AND `status <> 'delivered'` | `projects_org_id_status_idx`, `projects_org_id_archived_at_idx` |
| `deliverables` | N:1 `projects` (name, client name), N:1 `users` (uploader) | `status = 'ready'` AND `project_id IN (active project ids)` | `deliverables_org_id_status_created_at_idx` |
| `clients` | none | any row (archived included) | primary key within `org_id` |
| `clients` (addendum: active count) | none | `archived_at IS NULL` | `clients_org_id_archived_at_idx` |

**State transitions**: none. The page reads the invoice and project states (specs 0012 and 0010) and changes nothing.

**API surface**:

There is no Server Action and no route handler. The surface is one page and six server side reads in `src/dashboard/queries.ts`, each taking a `StaffContext`:

| Surface | Kind | Key inputs | Key outputs | Auth | Key errors |
|---|---|---|---|---|---|
| `/dashboard` | GET (Server Component page) | none (agency from the session) | header, then either the first run state or the Overview cards, the chart and the three detail sections | staff session, `(gated)` route group, proxy | a failed `hasAnyClient` read falls to the `(agency)` error boundary |
| `hasAnyClient(ctx)` | read | `ctx` | `boolean` | `StaffContext` | throws on a driver failure |
| `overdueInvoicesSummary(ctx, todayUtc)` | read | `ctx`, `todayUtc: string` | `{ count, totals: readonly { currency, cents }[], rows: readonly OverdueInvoiceRow[] }` (at most 5 rows) | `StaffContext` | throws on a driver failure, caught by its section |
| `openProjectsSummary(ctx, todayUtc)` | read | `ctx`, `todayUtc: string` | `{ count, rows: readonly OpenProjectRow[] }` (at most 5 rows) | `StaffContext` | same |
| `recentDeliverablesSummary(ctx, now)` | read | `ctx`, `now: Date` | `{ addedLast7Days, rows: readonly RecentDeliverableRow[] }` (at most 5 rows) | `StaffContext` | same |
| `activeClientsCount(ctx)` (addendum) | read | `ctx` | `number` | `StaffContext` | throws on a driver failure, caught by the Overview boundary |
| `invoicedTrend(ctx, todayUtc)` (addendum) | read | `ctx`, `todayUtc: string` | `{ months: readonly { month: string, totalsByCurrency: readonly { currency, cents }[] }[], currencies: readonly string[] }`, 6 `months` entries oldest first, `currencies` the sorted union of every currency appearing anywhere in the window | `StaffContext` | throws on a driver failure, caught by the chart's own boundary |

**Overview shares reads with the detail sections below it, rather than repeating them (addendum, cross checked).** `page.tsx` starts `overdueInvoicesSummary`, `openProjectsSummary` and `recentDeliverablesSummary` once each, unawaited, and passes the same promise to both `OverviewSection` and the matching detail section (`OverdueInvoicesSection`, `OpenProjectsSection`, `RecentDeliverablesSection`). Each consumer awaits the promise inside its own `<Suspense>` boundary and its own `try`/`catch`, so a shared promise resolves or rejects independently for each reader; nothing re-runs the query a second time, and nothing ties one section's paint to another's. `OverviewSection` additionally starts and awaits `activeClientsCount(ctx)` itself (the one read no detail section needs), inside the same `Promise.all`. To avoid reporting the same underlying failure twice, only the "owning" catch calls `reportException`: the existing detail section reports a failure in the promise it already reported before this addendum (`overdue_invoices`, `open_projects`, `recent_deliverables`); `OverviewSection`'s own catch reports only a failure that reaches it exclusively, which today is `activeClientsCount`, tagged `overview`. Either way Overview still renders its shared `ErrorState` for the whole card row on any of the four rejecting, per AC-24. The chart section, `InvoicedTrendSection`, is a second new async Server Component calling only `invoicedTrend`, which nothing else on the page reads.

The page resolves `agencyContext()`, `currentAgency()`, `todayUtc()` and `now` once, outside any section, and passes `ctx`, `todayUtc` and `now` to each section as props, plus (addendum) the three shared summary promises described above. A section never resolves the context itself, so the context lookup's own `redirect("/onboarding")` repair path (`src/auth/context.ts`) can never land inside a section's `catch`. Each detail section component (`OverdueInvoicesSection`, `OpenProjectsSection`, `RecentDeliverablesSection` in `src/dashboard/ui/`) awaits its assigned promise inside a `try`/`catch` (addendum: the shared promise it now receives as a prop, in place of calling the summary function itself). The `catch` first calls `unstable_rethrow(error)` from `next/navigation`, so any Next.js control flow signal passes through untouched. For a real failure it then calls `reportException(error, { tags: { section }, fingerprint: ["dashboard_section_failed", section] })` and renders `ErrorState`. The shared frame (heading, count line, list, footer link) is one `DashboardSection` component, and the loading placeholder is one `DashboardSectionSkeleton`.

How each read works (these are the calls, not a menu):
- **`overdueInvoicesSummary`** loads every matching invoice row, with `with: { client: { columns: { name: true } } }`, through `tenantDb(ctx).findMany` (the accessor has no top level `columns` option, so the invoice rows come back whole), then hands them to a pure `summariseOverdue(rows, todayUtc)`. That function computes the count, the per currency sums and the sorted top 5 with `daysOverdue`. The overdue set is small by nature (it is debt that has not been chased), and the accessor has `count` but no `sum`, so the totals are summed in memory in integer cents.
- **`openProjectsSummary`** runs `tenantDb(ctx).count(projects, { where })` and `findMany(projects, { where, orderBy, limit: 5, with: { client } })` in parallel, then maps `overdue` through the existing `isOverdue`.
- **`recentDeliverablesSummary`** first reads the ids of the agency's active projects (`archived_at IS NULL`). With none, it returns zero rows without a second query. Otherwise it runs `count(deliverables, { where: ready AND projectId in ids AND createdAt > now - 7 days })` (strictly later, with `gt`) and `findMany(deliverables, { where: ready AND projectId in ids, orderBy: [createdAt desc, id desc], limit: 5, with: { project: { with: { client } }, uploadedBy } })` in parallel. This stays inside the accessor's typed `where` with no raw SQL subquery, matching every other feature read.
- **`hasAnyClient`** is `tenantDb(ctx).findFirst(clients) !== undefined`.
- **`activeClientsCount`** (addendum) is `tenantDb(ctx).count(clients, { where: isNull(clients.archivedAt) })`.
- **`invoicedTrend`** (addendum) computes the window's start with a new pure `sixMonthWindowStart(todayUtc)` in `src/lib/dates.ts` (the first day of the UTC calendar month five months before `todayUtc`'s month), reads every invoice with `tenantDb(ctx).findMany(invoices, { where: and(inArray(invoices.status, ["sent", "overdue", "paid"]), gte(invoices.issueDate, windowStart)) })`, then hands the rows to a pure `summariseInvoicedByMonth(rows, todayUtc)`. That function buckets each row by the UTC year month of its `issue_date`, stored as `"YYYY-MM"` (e.g. `"2026-04"`), and by its `currency`, sums `total_cents` per bucket, and returns exactly 6 months (oldest first, each including months with no invoices as an empty `totalsByCurrency`) plus `currencies`, the sorted union of every currency with a non zero bucket anywhere in the window. This mirrors `summariseOverdue`'s in memory sum, for the same reason: the window is small by construction. `InvoicedTrendSection` formats each `"YYYY-MM"` month for display with `Intl.DateTimeFormat` pinned to `timeZone: "UTC"` (e.g. `"Apr 2026"`), draws the y axis in compact whole units with no currency symbol (the chart can hold more than one currency, so no single symbol is correct), and labels each hovered point with `formatMoney(cents, currency)` plus the currency code as text in the tooltip.

**On the new sections' error handling (addendum, cross checked):** `OverviewSection` and `InvoicedTrendSection` follow the same `unstable_rethrow` then `reportException` then `ErrorState` shape as the three existing sections, but read the settled promises immutably rather than reassigning a `let`: a small `settle<T>(promise: Promise<T>): Promise<{ ok: true, value: T } | { ok: false, error: unknown }>` helper (`src/dashboard/settle.ts`) wraps each `await` in its own `try`/`catch`, calls `unstable_rethrow(error)` first exactly as the existing sections do (so a Next.js control flow signal still passes through untouched even though none of these reads throw one today), and only then returns a `Result` rather than throwing past the caller, matching this project's rule that expected failures return as values (root `AGENTS.md`, Rules). `Promise.all` over four `settle()` calls, then one `.find((r) => !r.ok)` decides whether the section renders its cards or its shared `ErrorState`, with no mutable local variable anywhere in the section.

**Key invariants**:
- Every read goes through `tenantDb(ctx)`. Nothing in `src/dashboard/` imports `src/db/client.ts` or uses `withSystemAccess` (ESLint enforces both already).
- The overdue rule has one definition: `status === "overdue" || isPastDue(...)`. The SQL `where` and the pure `summariseOverdue` agree, and a unit test holds them together over the same fixtures.
- The dashboard's open project count equals the total `/projects` shows with no filters. Its top 5 equal that list's first 5 rows.
- The overdue count can exceed what `/invoices?status=overdue` lists, only by `sent` invoices whose due date passed since the last nightly sweep (at most one day's worth). This is accepted and known (see Consequences).
- Money is integer cents until `formatMoney`. Currencies are never added together.
- "Today" is read once per request, and "now" is read once per request. No section reads the clock itself.
- The page writes nothing and emits no analytics event.
- The Overview card headlines and the matching detail sections below them read the same settled promise (addendum, cross checked), so they can never disagree within one page load; a write landing between two separate page loads is still possible, the same accepted gap the existing count and rows tradeoff already documents.
- The chart's per currency sums are integer cents until `formatMoney`, the same rule as every other total on this page.
- Every new `--chart-1`..`--chart-4` token reaches at least 3:1 contrast against `--card` in both themes (addendum, cross checked), the WCAG non text contrast floor for a graphical object like a chart line, checked the same way `contrast.test.ts` already checks every other token pair.

**Security model**:
- Readers: signed in agency staff (admin or member) of the acting agency, with full access (the `(gated)` layout's subscription gate). Both roles see the same content, because both can already read every invoice, project and deliverable on their own pages.
- Client contacts never reach `/dashboard`. The proxy redirects them, as for every agency route.
- No new data leaves the server beyond what the linked pages already show. No file URL or R2 key is ever rendered (rows link to the project page, never to a download).
- No regulated data scope. Invoice totals are business records, and no payment data exists on this platform.
- Section error messages never include a driver message, a digest or an id beyond what `ErrorState` already allows.

**Configuration required**: none. No new environment variable, secret or provider setup.

## Consequences

**Positive**:
- The first screen after sign in finally answers "what needs me today", which the scope has promised since spec 0004.
- No schema, no migration, no new provider, and no new write path. The feature cannot corrupt data.
- The overdue rule, the project overdue rule, "today" and money formatting are reused, not copied, so the dashboard can't drift from the pages it links to.
- One flaky read degrades one section, not the whole page.
- The Overview row and the chart (addendum) give agency staff a sense of scale and trend before they read a single list, which the three lists alone could not.

**Negative / tradeoffs**:
- The overdue count can be a little ahead of `/invoices?status=overdue` for up to a day (sent invoices past due before the nightly sweep runs). A careful user may notice the mismatch after clicking "View all".
- `overdueInvoicesSummary` loads every overdue invoice to sum it in memory. That is fine at realistic agency volumes (tens, not thousands), but it has no ceiling. A sum on the accessor would be the fix if it ever measures slow.
- `recentDeliverablesSummary` passes the active project ids as an `IN` list. That is fine into the low thousands of projects, but an agency far beyond that would want a join, which needs the tenant layer to grow a new reader.
- Up to seven small queries per page load: the client check, one overdue read, a count and rows for projects, and the active project ids plus a count and rows for deliverables. There is no caching, by choice, so every visit hits the database. **(Addendum, cross checked)** the addendum adds two more: `activeClientsCount` and `invoicedTrend`'s single read; the three shared reads add no further queries, since Overview consumes the same promise the matching detail section already started.
- The client check runs before the three sections can start, because it decides the page's shape. The header paints first, but the three parallel reads wait one query behind it.
- Each section's count and rows are two separate queries with no shared snapshot, so a write landing between them can briefly make the headline and the rows disagree (e.g. "6 open projects" above a list reflecting 7). The next load corrects it. This is accepted, like the invoice filter gap. The runner up, one read transaction per section, would hold a pooled connection for no user visible gain.
- The agency's default currency no longer shows on the dashboard (it lived in the welcome panel). It remains on `/settings`.
- **(Addendum, cross checked)** Overview's four stat reads share one `<Suspense>`/error boundary rather than four, so one failing read (say, `activeClientsCount`) blanks all four cards, not just its own. This is a deliberate simplification for four small counts; the three detail sections keep their own individual boundaries.
- **(Addendum, cross checked)** Sharing a promise between Overview and a detail section means the two are coupled by construction: if a future change ever needs Overview's overdue card to show a different number than the detail section's headline, they can no longer diverge without giving Overview its own separate read again.
- **(Addendum)** `invoicedTrend` sums every matching invoice in memory over a fixed six month window, the same shape of tradeoff as `overdueInvoicesSummary`: fine at realistic volumes, no ceiling.
- **(Addendum)** The chart adds shadcn's `chart` primitive, wrapping Recharts, as this project's first non shadcn native runtime dependency in the UI area. It is a small, actively maintained library, but it is still new operational surface (bundle size, an SVG renderer to keep working across a React major version) that the project did not carry before.
- **(Addendum)** The new `--chart-1`..`--chart-4` tokens must be added to `src/ui/contrast.ts`'s measured pairs by hand; nothing enforces that a new token gets a contrast test written for it.

**Neutral**:
- `src/dashboard/` is a new feature folder. `/sync` will want a line for it, and possibly a nested `AGENTS.md` if it grows.
- `AgencyWelcome` loses its only caller. Delete it with its test in this feature, or keep it if `/settings` wants it (a build time call).
- `formatBillingDate` lives in `src/payments/` but is used for a deliverable date, as the project page already does.
- **(Addendum)** The chart's rendered SVG carries `aria-hidden="true"` and the `sr-only` table is its sole accessible form, rather than both being announced.
